LESSON 11

Think Like a Product Builder

Before writing more code, choose a real problem, design a small useful experience, and make a plan you can actually finish.

User needsMVP & scope Acceptance criteriaAI-assisted planning
The mission

Turn an idea into an actionable plan

In lesson 10 we asked how a project runs. Today we ask a question that comes even earlier: what should we build, for whom, and why? You may extend SpaceBuddy or choose another idea that interests you.

  • Describe a specific user, their problem, and an outcome worth testing.
  • Choose a small minimum viable product (MVP) and explain what is deliberately excluded.
  • Break one user journey into 3–5 prioritized tasks and write testable acceptance criteria.
  • Use AI to challenge the plan while keeping the decisions and verification yours.
One-hour session

Our route today

  1. 10 min — Review: show lesson 10's demo or describe where you got stuck; identify what is already working.
  2. 15 min — Discover: choose a user, problem, and one desired outcome.
  3. 25 min — Plan together: map a journey, cut scope, and write tasks and acceptance criteria.
  4. 10 min — Challenge and explain: review an AI suggestion, name a risk, and agree on homework.

Keep this as a conversation and a short written plan. You do not need a finished bot or cloud deployment to take part.

Start with the person

Find the problem behind the feature

“Build an AI-powered space app” names a solution, not a user need. A stronger starting point describes who is trying to do what, why it is difficult, and how you could learn whether your idea helps.

User

Who has the problem? Start with one specific type of person, not “everyone.”

Problem

What are they trying to do, and what makes it inconvenient or confusing today?

Outcome

What observable result would show that this small version is useful?

Worked example: SpaceBuddy

User: A student interested in astronomy who already uses Telegram.

Problem: They want to find and revisit NASA's Astronomy Picture of the Day for a particular date without searching through multiple pages.

Proposed outcome: In a supervised demo, the student can request one valid date and find that image again in their favorites.

This is a hypothesis, not proof that all astronomy students need the feature. Ask the mentor or a willing tester whether the problem and journey make sense. Record what you observed rather than claiming broad demand from one conversation.

Respect privacy: Ask permission before testing with another person. Use fictional or non-sensitive examples in notes and AI prompts; do not collect personal information just to validate an idea.
Your turn: Write one sentence: “For [user], it is difficult to [goal] because [problem].” What would you ask a potential user to check your assumption?
Make the first version smaller

Map one journey, then define the MVP

An MVP is a small version that can test an important idea with a user. “Minimum” does not mean ignoring basic safety or obvious errors: it means leaving out features that are not needed for this particular learning goal.

One possible SpaceBuddy journey

  1. The user sends a date to the bot.
  2. The bot checks the date and retrieves the corresponding NASA image.
  3. The user saves it as a favorite and later asks to see their saved items.

If any of this already exists, inspect and reuse it rather than rebuilding it. If the current bot is incomplete, the plan can focus on completing just this journey. A different project can use a similarly small journey.

Scope challenge: A suggested feature sounds exciting but adds a week of work. Ask: “Does the user need this to complete the chosen journey?” If not, place it in a later list.
Make the plan executable

From journey to prioritized tasks

Tasks are small pieces of work; acceptance criteria describe observable behavior that must be true when a feature is done. Sort by user value and prerequisites, then estimate roughly. Estimates are guesses to revisit, not promises.

Example backlog

OrderTaskWhy now?
1Inspect the existing bot and list what worksAvoid duplicating lesson 9 work; discover gaps.
2Complete or verify date lookup and validationThe user needs an image before saving it.
3Complete or verify save and list favoritesCloses the main user journey.
4Test happy path and failure cases with safe test dataChecks that the journey is reliable enough to demo.
5Document and demonstrate the journeyA tester can understand and try the result.

These are planning examples, not claims about the current code. Break any item that feels too large into smaller steps; mark completed work instead of implementing it again. Keep the first implementation slice small enough for your available time.

Write criteria someone else can check

For the date lookup feature, a simple Given / When / Then format separates the starting condition, action, and expected result:

Example acceptance criteria · date lookup
Given a valid date with an available image
When the user requests that date
Then the bot displays the image and its title.

Given a date that is invalid or outside the supported range
When the user requests it
Then the bot explains the problem and does not request NASA data.

Given the NASA service is unavailable
When the user requests an otherwise valid date
Then the bot reports the failure and remains usable.

Pick a specific supported date range when implementing, based on the API's documentation. Test the normal path and failure behavior with controlled responses where practical, rather than relying only on a live API.

Try it: Rewrite “make favorites better” as one user-facing story and two observable acceptance criteria. How will you tell whether each criterion passed?

Pick a planning tool

Markdown checklist

Good for a small solo plan next to the code. Easy to review in a pull request.

GitHub Issues

Useful for tracking individual tasks, decisions, and discussion. See GitHub's guide.

Project board

A visual way to move tasks through “to do,” “in progress,” and “done.” Helpful when the list gets harder to follow.

Choose one; the tool is not the goal. A simple checklist is enough for this lesson. Whether a task is on a board or in a file, keep its purpose and acceptance criteria clear.

AI-assisted planning

Ask for options, then make the decisions

AI can suggest user stories, missing cases, and smaller tasks. It cannot know your user's needs or your existing code unless you provide accurate context, and its confident estimates may be wrong.

Example prompt · replace the brackets
I am planning [one-sentence project idea] for [specific user].
The user wants to [goal]. My current project already has [known facts].
I have [available time] and want to avoid [constraints].

Suggest a single small user journey, 3–5 prioritized tasks, and
two testable acceptance criteria for one task. List assumptions,
one risk, and features to defer. Do not write code.

Review a hypothetical suggestion

Suppose AI proposes “add social accounts, recommendation AI, and paid cloud hosting before the first demo.” Compare that with the original user journey and constraints. Which suggestions add cost, dependencies, or complexity without proving the core idea?

  1. Inspect: separate facts you verified from assumptions AI invented.
  2. Cut: keep only what supports the chosen journey and constraints; defer the rest.
  3. Verify: check project state, relevant documentation, and feasibility with the mentor or a safe prototype.
  4. Explain: record one suggestion you accepted or changed and why.
Do not share secrets or private information: Use placeholders for tokens, private messages, user data, and other sensitive context. AI output is a draft, not evidence that a feature is needed or an estimate is accurate.
Knowledge check

Can you defend the plan?

Answer aloud first; then open each explanation.

1. How is a problem different from a feature?

A problem describes a user's difficulty or goal. A feature is one possible way to address it; other solutions may work better.

2. Why exclude a feature from the MVP?

If it is not needed to test the chosen journey, deferring it saves time and reduces complexity. Record it for later rather than silently losing the idea.

3. Is “make the bot user-friendly” a testable acceptance criterion?

Not by itself. Describe an observable action and result, such as a clear error message for an invalid date, and agree how to check it.

4. What should happen if a task is already implemented?

Inspect and verify the existing behavior, then mark the task done or revise the plan. Do not rebuild it merely to match an example backlog.

5. Does an AI-generated estimate guarantee a task will fit?

No. It may miss project details or dependencies. Treat it as a rough hypothesis, check the actual project, and adjust as you learn.

6. What can one tester tell you?

They can reveal a problem or give feedback about their experience. One successful demo does not prove broad demand or represent every user.

Homework · 90–120 minutes

Write your one-page project brief

Core goal: plan one small SpaceBuddy extension or a project of your choice. Write in a Markdown file in your project repository, or use a document if the repository is not ready. This is a planning assignment: implementation is optional.

  1. Choose and investigate (20–25 min): describe the user, problem, and current project state. List one assumption and how you could check it with a willing person or a small test.
  2. Define the MVP (20–25 min): write one user journey, an observable success check, constraints, and at least one feature you are deferring.
  3. Plan the work (25–30 min): write 3–5 prioritized tasks and rough time estimates. Add testable acceptance criteria for one feature, including a failure or edge case. Identify one risk and a practical response.
  4. Challenge and share (25–40 min): ask AI for feedback using sanitized context; record one suggestion you accepted or changed and why. Review the brief with your mentor, or share it for the next lesson.

Definition of done

Optional stretch: Turn one task into a GitHub issue or try a tiny prototype that tests your riskiest assumption. Note what you learned; do not expand the MVP just because a tool suggested it.
Stuck? Pick the SpaceBuddy example, make a reasonable assumption, and label it as unverified. Bring the assumption and your question to the mentor rather than trying to perfect the whole project alone.
