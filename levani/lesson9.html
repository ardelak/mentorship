1 Part 1 · Computer Science Theory (20 min)

From Flat Files to Relational Databases

Why professional software uses Relational Database Management Systems (RDBMS) instead of JSON files.

In Lesson 6, we used a local JSON file (nasa_cache.json) to cache asteroid data. While flat files (JSON, CSV, TXT) are great for temporary single-user scripts, they break down completely when used as the primary storage for a multi-user application like Space_Buddy-Bot.

The 4 Limitations of a File-Based Approach

  • 1. Data Redundancy & Inconsistency: If you store a user's username and first_name inside every saved APOD dictionary in a JSON file, that user's name is duplicated 50 times. If they change their Telegram handle, updating some records but missing others causes data inconsistency.
  • 2. Concurrency & Race Conditions: Imagine User A and User B click "Save Photo" at the exact same millisecond. Both Python threads read favorites.json, append their item in RAM, and overwrite the file on disk. Whoever finishes 1 millisecond later completely erases the first user's save!
  • 3. O(N) Full-File Scans: To check if User 981234 saved a photo from 2024-05-12, Python must load the entire JSON file into RAM and loop through thousands of items one by one.
  • 4. Lack of Data Integrity & Program-Data Dependence: A JSON file doesn't stop a bug from saving an integer where a URL string should be. Furthermore, if you change the structure of the JSON file, every Python script that reads it must be rewritten.
ABSTRACTION IN DATABASES

A Database Management System (DBMS) provides abstraction: when you run a query like SELECT title FROM saved_apods WHERE user_id = 42, you only specify what data you want. The DBMS hides the complex physical details of how bytes are indexed on the SSD, how file locks are managed, and how memory buffers are searched.

Core Relational Database Terminology

In 1970, Edgar F. Codd invented the Relational Model, which organizes data into separate, linked two-dimensional tables (called relations) to eliminate redundancy.

Relational Term Everyday / Table Term Space_Buddy-Bot Example
Entity Real-world object being modeled A Telegram User, or a Saved NASA Photo
Relation / Table Grid of rows and columns users table, saved_apods table
Tuple / Record A single horizontal Row (1049281, 'alex_dev', 'alex', '2026-11-07')
Attribute / Field A single vertical Column apod_date, image_url, username
Primary Key (PK) Unique identifier for a row user_id in users (never NULL, always unique)
Foreign Key (FK) Column linking to another table's PK user_id inside saved_apods pointing to users.user_id

Keys, Relationships & Referential Integrity

How do tables talk to each other without duplicating data? Through Keys and Relationships:

  • Candidate Key vs. Primary Key vs. Secondary Key: Any attribute that could uniquely identify a row is a Candidate Key (e.g., user_id). The one we choose as the official identifier is the Primary Key (PK). An attribute used frequently for searching (like apod_date) that has an Index attached to speed up lookups from $O(N)$ to $O(\log N)$ is called a Secondary Key.
  • One-to-Many (1:M) Relationship: One user in the users table can save Many photos in the saved_apods table. We model this by placing the user's Primary Key (user_id) into the saved_apods table as a Foreign Key (FK).
  • Referential Integrity: A critical DBMS rule stating that every Foreign Key value must match an existing Primary Key in the parent table. You cannot save a favorite APOD for user_id = 99999 if User 99999 does not exist in the users table (preventing "orphan records").

NORMALIZATION: WHY OUR DESIGN IS IN 3NF (THIRD NORMAL FORM)

Database designers use Normalization to remove redundancy:

• 1NF (First Normal Form): Every cell holds a single atomic value (no comma-separated lists like "2024-01-01, 2024-05-12" inside one cell).

• 2NF (Second Normal Form): In 1NF, and every non-key column depends on the whole Primary Key.

• 3NF (Third Normal Form): In 2NF, with no transitive dependencies—meaning non-key columns depend only on the Primary Key. In saved_apods, we do NOT store username because username depends on user_id, not on the bookmark id. Separating them into two tables achieves clean 3NF!

2 Part 2 · The SQLite Engine & DDL (15 min)

How SQLite Works & Building the Schema

Serverless architecture, ACID transactions, and Data Definition Language (DDL).

Most database engines (like PostgreSQL, MySQL, or Oracle) are Client-Server systems: they run as a separate background service listening on a network port. SQLite is different—it is an embedded, serverless relational database built directly into Python's standard library (import sqlite3).

Why SQLite is the World's Most Deployed Database Engine

  • Zero Configuration: No server to install or pay for. The entire database—tables, indices, and datadictionary—lives inside a single cross-platform binary file (space_buddy.db) right inside your project folder.
  • ACID Transactions: Even if the power goes out or your Python script crashes mid-save, SQLite guarantees Atomicity (all steps of a save succeed, or none do), Consistency, Isolation, and Durability.
  • Real-World Applications: Every iPhone, Android phone, web browser (Chrome/Firefox history), macOS, and aircraft flight software uses SQLite internally, and it easily handles 100,000+ daily bot requests.

SQL Sub-Languages: DDL vs. DML

Structured Query Language (SQL) is divided into specialized command categories:

  • DDL (Data Definition Language): Defines the database structure/schema (CREATE TABLE, ALTER TABLE, DROP TABLE, CREATE INDEX).
  • DML (Data Manipulation Language): Reads and modifies rows inside the tables (INSERT, SELECT, UPDATE, DELETE).

Let's create a new package folder database/ in Space_Buddy-Bot and write our database manager using DDL to initialize our two tables:

database/db_manager.py (Part 1: Connection & DDL Schema)
import sqlite3
from datetime import datetime, timezone


class DatabaseManager:
    """Manages SQLite connections and table schemas for Space_Buddy-Bot."""

    def __init__(self, db_path: str = "space_buddy.db"):
        self.db_path = db_path
        self._create_tables()

    def _get_connection(self) -> sqlite3.Connection:
        """Opens a connection with Row factory and Foreign Key enforcement."""
        conn = sqlite3.connect(self.db_path)
        # sqlite3.Row allows accessing columns by name: row["title"] instead of row[2]
        conn.row_factory = sqlite3.Row
        # Enforce Referential Integrity (Foreign Keys) on every connection
        conn.execute("PRAGMA foreign_keys = ON;")
        return conn

    def _create_tables(self) -> None:
        """Executes DDL statements to create normalized 3NF tables if missing."""
        # Using 'with' automatically commits transactions or rolls back on error!
        with self._get_connection() as conn:
            cursor = conn.cursor()

            # Table 1: Telegram Users (Parent Entity)
            cursor.execute("""
                CREATE TABLE IF NOT EXISTS users (
                    user_id     INTEGER PRIMARY KEY,
                    username    TEXT,
                    first_name  TEXT NOT NULL,
                    joined_at   TEXT NOT NULL
                );
            """)

            # Table 2: Saved APOD Favorites (Child Entity with Foreign Key & UNIQUE constraint)
            cursor.execute("""
                CREATE TABLE IF NOT EXISTS saved_apods (
                    id          INTEGER PRIMARY KEY AUTOINCREMENT,
                    user_id     INTEGER NOT NULL,
                    apod_date   TEXT NOT NULL,
                    title       TEXT NOT NULL,
                    media_url   TEXT NOT NULL,
                    saved_at    TEXT NOT NULL,
                    FOREIGN KEY (user_id) REFERENCES users (user_id) ON DELETE CASCADE,
                    UNIQUE (user_id, apod_date)
                );
            """)
PRO PATTERN: COMPOSITE UNIQUE CONSTRAINT

Notice UNIQUE (user_id, apod_date) at the bottom of saved_apods. This tells SQLite: "User A and User B can both save the photo from 2024-05-12, and User A can save 100 different dates, but User A cannot save 2024-05-12 twice!"

Step 1: Environment-Based Database Switching & WAL Concurrency

When you run your bot AND open a database viewer (or local SQLite web server) at the same time, two programs access the .db file simultaneously. By default, SQLite locks the entire file during writes, which can trigger sqlite3.OperationalError: database is locked.

To prevent this during local testing and production, we enable WAL (Write-Ahead Logging) mode (PRAGMA journal_mode = WAL;), which allows multiple readers and a writer to work concurrently:

config.py & database/db_manager.py (Local Dev Ready)
# --- In config.py ---
import os
from dotenv import load_dotenv

load_dotenv()

NASA_API_KEY = os.getenv("NASA_API_KEY", "DEMO_KEY")
TELEGRAM_BOT_TOKEN = os.getenv("TELEGRAM_BOT_TOKEN", "")
# Defaults to dev_space_buddy.db locally; override in .env for production
DATABASE_PATH = os.getenv("DATABASE_PATH", "dev_space_buddy.db")


# --- Inside DatabaseManager._get_connection() in database/db_manager.py ---
def _get_connection(self) -> sqlite3.Connection:
    # timeout=10.0 tells SQLite to wait up to 10s if another process is writing
    conn = sqlite3.connect(self.db_path, timeout=10.0)
    conn.row_factory = sqlite3.Row
    # Enable WAL mode so our local SQLite Web Server and Bot can run side-by-side!
    conn.execute("PRAGMA journal_mode = WAL;")
    conn.execute("PRAGMA foreign_keys = ON;")
    return conn

Step 4: True In-Memory (:memory:) Testing Architecture

There is one subtle catch with sqlite3.connect(":memory:"): every time you call sqlite3.connect(":memory:"), SQLite creates a brand-new, blank RAM database—and the moment that connection closes, the RAM database is wiped! If your DatabaseManager opens a new connection inside every method, :memory: would forget its tables between _create_tables() and register_user().

To support both disk files and persistent :memory: unit testing, we keep a single shared connection alive when db_path == ":memory:":

database/db_manager.py (Supporting Both Disk & :memory: Mode)
class DatabaseManager:
    def __init__(self, db_path: str = "space_buddy.db"):
        self.db_path = db_path
        # If using ":memory:" for fast unit tests, keep one persistent connection open
        self._memory_conn: sqlite3.Connection | None = None
        if self.db_path == ":memory:":
            self._memory_conn = self._create_raw_connection()
        self._create_tables()

    def _create_raw_connection(self) -> sqlite3.Connection:
        conn = sqlite3.connect(self.db_path, timeout=10.0)
        conn.row_factory = sqlite3.Row
        conn.execute("PRAGMA journal_mode = WAL;")
        conn.execute("PRAGMA foreign_keys = ON;")
        return conn

    def _get_connection(self) -> sqlite3.Connection:
        if self._memory_conn is not None:
            return self._memory_conn
        return self._create_raw_connection()

    def close(self) -> None:
        """Closes the persistent in-memory connection after unit tests finish."""
        if self._memory_conn is not None:
            self._memory_conn.close()
            self._memory_conn = None

Zero-Disk Unit Testing with DatabaseManager(":memory:")

3 Part 3 · DML, CRUD & Security (20 min)

CRUD Operations & SQL Injection Defense

Writing safe Data Manipulation Language (DML) queries in Python.

Every database-driven feature in software engineering maps to the four CRUD operations:

  • C — Create: INSERT INTO table ... (Registering a user or saving an APOD photo).
  • R — Read: SELECT ... FROM table WHERE ... (Fetching a user's saved collection or joining tables).
  • U — Update: UPDATE table SET ... WHERE ... (Updating a user's Telegram username if it changed).
  • D — Delete: DELETE FROM table WHERE ... (Removing a bookmark).
SECURITY CRITICAL: NEVER USE F-STRINGS IN SQL QUERIES!

If you format user input into a SQL string using an f-string, a malicious user can set their Telegram name to Robert'); DROP TABLE users; --. The database will execute their text as a command and destroy your tables! This attack is called SQL Injection (SQLi).

Always use Parameterized Queries with ? placeholders and pass variables as a separate tuple: cursor.execute("SELECT * FROM users WHERE user_id = ?", (user_id,)).

sql_injection_comparison.py
# ❌ VULNERABLE TO SQL INJECTION (Never write this!)
cursor.execute(f"SELECT * FROM saved_apods WHERE apod_date = '{user_input}'")

# ✅ SAFE PARAMETERIZED QUERY (The SQLite driver neutralizes any malicious symbols)
# Note the trailing comma in (user_input,) to make a 1-element Python tuple!
cursor.execute("SELECT * FROM saved_apods WHERE apod_date = ?", (user_input,))

Implementing Full CRUD + Relational JOIN in DatabaseManager

Let's add methods to register users (INSERT OR UPDATE), bookmark APODs (INSERT OR IGNORE), fetch a user's saved gallery (SELECT), delete bookmarks (DELETE), and run an analytical INNER JOIN across both tables.

database/db_manager.py (Part 2: CRUD & JOIN Methods)
    def register_user(self, user_id: int, username: str, first_name: str) -> None:
        """Inserts a new user or updates their username if they already exist."""
        now = datetime.now(timezone.utc).strftime("%Y-%m-%d %H:%M:%S")
        with self._get_connection() as conn:
            conn.execute("""
                INSERT INTO users (user_id, username, first_name, joined_at)
                VALUES (?, ?, ?, ?)
                ON CONFLICT(user_id) DO UPDATE SET
                    username = excluded.username,
                    first_name = excluded.first_name;
            """, (user_id, username or "anonymous", first_name, now))

    def save_apod(self, user_id: int, apod_date: str, title: str, media_url: str) -> bool:
        """Saves an APOD to favorites. Returns True if newly saved, False if duplicate."""
        now = datetime.now(timezone.utc).strftime("%Y-%m-%d %H:%M:%S")
        with self._get_connection() as conn:
            cursor = conn.execute("""
                INSERT OR IGNORE INTO saved_apods (user_id, apod_date, title, media_url, saved_at)
                VALUES (?, ?, ?, ?, ?);
            """, (user_id, apod_date, title, media_url, now))
            # rowcount is 1 if a new row was inserted, or 0 if ignored due to duplicate
            return cursor.rowcount > 0

    def get_user_favorites(self, user_id: int, limit: int = 5) -> list[dict]:
        """Fetches a user's most recently saved APODs as a list of dictionaries."""
        with self._get_connection() as conn:
            cursor = conn.execute("""
                SELECT id, apod_date, title, media_url, saved_at
                FROM saved_apods
                WHERE user_id = ?
                ORDER BY apod_date DESC
                LIMIT ?;
            """, (user_id, limit))
            return [dict(row) for row in cursor.fetchall()]

    def delete_favorite(self, user_id: int, apod_date: str) -> bool:
        """Deletes a specific APOD date from a user's favorites."""
        with self._get_connection() as conn:
            cursor = conn.execute("""
                DELETE FROM saved_apods
                WHERE user_id = ? AND apod_date = ?;
            """, (user_id, apod_date))
            return cursor.rowcount > 0

    def get_recent_community_saves(self, limit: int = 5) -> list[dict]:
        """Uses an INNER JOIN to combine user names with their saved APOD titles."""
        with self._get_connection() as conn:
            cursor = conn.execute("""
                SELECT u.first_name, u.username, s.apod_date, s.title
                FROM saved_apods s
                INNER JOIN users u ON s.user_id = u.user_id
                ORDER BY s.saved_at DESC
                LIMIT ?;
            """, (limit,))
            return [dict(row) for row in cursor.fetchall()]

The APOD Time Machine & Inline Buttons

Adding historical date validation in nasa_service.py and interactive Telegram buttons.

One of our key goals for Space_Buddy-Bot is allowing users to explore astronomy pictures from any date in history (for example, their birthday: /apod 2005-08-19) and bookmarking them with a single tap.

Step A: Validating APOD Dates in services/nasa_service.py

NASA's APOD archive launched on June 16, 1995 (1995-06-16). If a user requests a date before that, or a date in the future, we should catch it cleanly in Python before wasting an API request.

services/nasa_service.py
from datetime import date, datetime
import requests
from config import NASA_API_KEY

APOD_FIRST_DATE = date(1995, 6, 16)


def validate_apod_date(date_str: str) -> tuple[bool, str]:
    """
    Validates a YYYY-MM-DD string against NASA APOD archive bounds.
    Returns (is_valid, clean_date_or_error_message).
    """
    try:
        parsed_date = datetime.strptime(date_str.strip(), "%Y-%m-%d").date()
    except ValueError:
        return False, "⚠️ Invalid format! Please use YYYY-MM-DD (e.g., `/apod 2024-05-12`)."

    today = date.today()
    if parsed_date < APOD_FIRST_DATE:
        return False, "🔭 NASA's APOD archive started on 1995-06-16! Pick a later date."
    if parsed_date > today:
        return False, "🚀 Even NASA can't photograph the future yet! Pick today or earlier."

    return True, parsed_date.isoformat()


def fetch_apod(apod_date: str | None = None) -> dict:
    """Fetches APOD data from NASA API for today or a specific YYYY-MM-DD date."""
    url = "https://api.nasa.gov/planetary/apod"
    params = {"api_key": NASA_API_KEY}
    if apod_date:
        params["date"] = apod_date

    response = requests.get(url, params=params, timeout=10)
    response.raise_for_status()
    return response.json()

Preparing for 24/7 Cloud Hosting

Packaging dependencies, protecting .gitignore, and running resilient polling in the cloud.

Right now, if you close VS Code or shut down your computer, Space_Buddy-Bot goes offline. To keep it running 24/7, we deploy our repository to a cloud Linux container (such as PythonAnywhere, Railway, or Render).

The 3 Golden Rules of Cloud Bot Deployment

  • 1. Freeze Your Dependencies (requirements.txt): The cloud server starts as a blank Linux machine. It reads requirements.txt to know which packages (pyTelegramBotAPI, requests, python-dotenv) to install.
  • 2. Never Commit .db or .env Files to GitHub: Your space_buddy.db file contains live user data, and .env contains secret keys. Both belong in .gitignore! Your Python code will automatically create space_buddy.db on the server the first time DatabaseManager() runs.
  • 3. Resilient Polling & Structured Logging: Cloud networks occasionally drop connections for a second. We wrap bot.infinity_polling() with logging so we can inspect server logs anytime.

class TestDatabaseAndValidation(unittest.TestCase):

        # Create a fresh temporary database file before each test

        self.temp_db.close()

        self.db.register_user(777, "alex", "alex")
