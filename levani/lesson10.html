Think before you build

What actually runs the project?

Suppose your bot works on your laptop. A fresh machine still needs a compatible Python version, the right packages, configuration, and somewhere to store its database. Writing down those needs is the first step toward a reproducible project.

Virtual environment

Separates Python packages for one project on a machine. You still manage Python and other system dependencies on that machine.

Docker image

A packaged filesystem and startup instructions, built from a Dockerfile. Think of it as a reusable blueprint.

Container

A running instance of an image. It has its own writable layer and can receive runtime configuration and mounted storage.

Host

The computer or cloud service running the process or container. Docker packages the app; it does not provide an always-on server.

Discuss: If you send a friend only your Python file, what else might they need? Name a dependency, a setting, and a piece of data.
Guided lab · offline example

Build it. Run it. Restart it.

This small SQLite counter works without Telegram, NASA, or API keys. It is a safe way to learn the workflow before adapting your own project.

Before starting: Install and start Docker Desktop or another Docker Engine setup. Open a terminal in a new, empty folder named lesson10-docker-demo. Run docker version and check that both client and server are available. The first build needs internet access to download the Python image.

1. Create a tiny application

Create app.py in that folder. Each run stores one visit in an SQLite database under /data.

app.py
import sqlite3

with sqlite3.connect("/data/visits.db") as db:
    db.execute("CREATE TABLE IF NOT EXISTS visits (id INTEGER PRIMARY KEY)")
    db.execute("INSERT INTO visits DEFAULT VALUES")
    count = db.execute("SELECT COUNT(*) FROM visits").fetchone()[0]

print(f"Saved visits: {count}")

2. Describe the image

Create a file named exactly Dockerfile in the same folder, with no extension. This example uses Python's built-in SQLite library, so it needs no package installation.

Dockerfile
FROM python:3.13-slim
WORKDIR /app
COPY app.py .
RUN mkdir -p /data
CMD ["python", "app.py"]
Read the recipe: FROM selects a base image; WORKDIR sets the working folder; COPY adds the app; RUN prepares a folder during the build; CMD supplies the default command when a container starts.

3. Build and compare runs

Run these commands from the folder containing both files. The final dot is the build context: the folder Docker can read while building.

Terminal · Windows, macOS, or Linux
docker build -t lesson10-demo .
docker run --rm lesson10-demo
docker run --rm lesson10-demo
docker run --rm --mount type=volume,source=lesson10-demo-data,target=/data lesson10-demo
docker run --rm --mount type=volume,source=lesson10-demo-data,target=/data lesson10-demo

The first two runs each print Saved visits: 1: --rm removes each stopped container and its writable layer. The last two runs should print 1 then 2 when using a new named volume. If the volume already exists, the count continues from its previous value.

Explain it back: Where is visits.db written in each pair of runs? What is removed, and what remains? A volume is separate from the container, but it is not automatically a backup or a cloud database.
Real data is different: This disposable demo uses Docker's default container user for simplicity. For a real deployment, consider a non-root user and storage permissions. Never put live user data in this exercise or delete a volume without knowing what it contains.

If something goes wrong

  • Cannot connect to Docker: start Docker Desktop/Engine and retry docker version.
  • Dockerfile not found: check the current folder and the exact filename, including hidden extensions.
  • Image build fails: read the first error; check internet access and the file contents before asking AI.
  • Count is not 1 then 2: check whether the named volume existed from an earlier run; a new volume starts fresh.
Choose the right tool

From local demo to running service

Deployment means making an application available in its intended environment. A cloud provider may build from a Git repository or run a Docker image. Choose based on what the app actually needs, not on how many tools you can add.

OptionUseful whenQuestion to ask
Run locallyLearning, development, and private demosWhat happens when the laptop sleeps?
Deploy from GitA host supports the language and application type directlyCan it run a continuously active worker, not just a website?
Deploy a Docker imageYou want more control over the runtime or a portable packageDoes the provider support this image and persistent storage?
Virtual serverYou need more control over the machineWho will maintain updates, access, and monitoring?

SpaceBuddy decision: a Telegram bot using long polling needs a running worker process, even though it does not serve a web page. A static-site host is not enough. Docker can package that worker, but a separate machine or service must keep it running.

Persistence checkpoint: A SQLite file inside a container's writable layer may disappear when the container is replaced. A local named volume demonstrates persistence on your own Docker host; it does not prove a cloud provider preserves data across redeployments. Check the provider's storage and backup guarantees, or choose an appropriate managed database. Consider SQLite's concurrency and backup needs before choosing it for a multi-user service.

Before any real deployment, check the provider's current worker support, storage, sleep/restart behavior, pricing, account requirements, and logs. A free tier or 24/7 availability is not guaranteed. Ask the mentor before creating a paid account or exposing the bot publicly.

Adapt the idea to SpaceBuddy

  1. First run the real project locally and identify its actual startup command, Python version, dependency file, and Telegram library. Lessons 7 and 9 show different libraries; use the one your project actually uses.
  2. Write a Dockerfile for that project: choose a compatible Python base, install the project's existing dependencies, copy the required source, and use its real startup command. Test it before considering hosting.
  3. Use a .dockerignore to exclude at least .env, virtual environments, Git metadata, and local database files from the build context. Pass secrets at runtime using the host's secret settings; for a local test, docker run --env-file .env ... can supply a correctly formatted local environment file. Do not copy secrets into the image or commit them.
  4. Identify the actual SQLite path. A volume mounted at /data only preserves the database if the application is configured to write its database there. Check permissions and verify persistence with non-sensitive test data.
  5. Stop the existing polling instance before starting another with the same bot token. Check logs and send a test message; a running process alone is not proof the bot works.

Keep .env and live databases out of Git too. A .gitignore does not remove a file already tracked or erase it from history; if a token was exposed, revoke or rotate it and ask the mentor for help.

AI as a teammate, not an autopilot

Ask, inspect, verify, explain

Give an assistant a narrow problem and constraints. Share only sanitized snippets: never paste tokens, private user data, or an entire secret file.

Example prompt · adapt to your project
I have a Python Telegram bot that uses [actual library] and SQLite.
It starts with [actual command] and stores its database at [path].
Suggest a simple Dockerfile and .dockerignore. Explain each instruction,
how runtime configuration is supplied, and what happens to the database
when the container is replaced. Do not include real secrets.

Your review: Does the suggestion use your real entry point and dependency file? Are secrets excluded from the build context? Does the database path match the proposed mount? Can you build, run, and test it? If any answer is unclear, ask a follow-up or inspect the Docker documentation.

Practice: Ask AI to explain one line of the lab Dockerfile. Check its explanation against the observed result and be ready to describe it in your own words.
Knowledge check

Can you explain your choices?

Answer aloud first; then open each explanation.

1. Is a Docker image the same as a running container?

No. An image is a packaged blueprint; a container is an instance created from it. One image can be used to create multiple containers.

2. Will Docker keep a bot online after your laptop shuts down?

No. The container needs a running host. To stay online when your laptop is off, the bot needs a suitable continuously running remote host.

3. Why did the demo count increase with a volume?

The database was written under the mounted /data directory. The named volume survived removal of the first container and was mounted into the next one.

4. Is a volume automatically a backup?

No. It separates storage from the container lifecycle, but data can still be lost or damaged. A real project needs a suitable backup and recovery plan.

5. Where should a bot token go?

Supply it at runtime through an appropriate secret mechanism, not in source code, an image, Git, screenshots, or an AI prompt. Rotate an exposed token.

6. What must you check before accepting an AI-generated Dockerfile?

Check that it matches your project, excludes secrets, handles data correctly, builds and runs successfully, and that you can explain its important instructions.

Homework · 90–120 minutes

Make a reproducible run

Core goal: complete and explain the offline lab. If your SpaceBuddy project already runs locally and there is time, adapt the approach to it. Do not deploy publicly or pay for hosting just to complete this assignment.

  1. Build and test (40–50 min): create the demo files, build the image, and run both pairs of commands. Record the observed counts and explain the difference.
  2. Document (20–25 min): add a short README with prerequisites, build and run commands, expected results, and what the volume preserves. Include the Dockerfile and app source in your homework branch or repository.
  3. Plan the real project (20–25 min): sketch SpaceBuddy's components and write down its actual startup command, dependency file, secret names without values, database path, and one possible hosting option. State what you still need to verify about storage, worker support, and cost.
  4. Review (10–20 min): use AI for one focused question, check its answer, run git status, and commit only the intended demo and documentation files. Share the branch or PR with your mentor.

Definition of done

Optional stretch: Containerize the actual bot using the adaptation checklist above. Use test data and stop the existing polling process first. Record a successful test message; do not assume that the demo's /data path or startup command matches your project.
Stuck? After 10 minutes, note the command, the exact error, and what you tried; ask your mentor. Remove tokens, personal data, and other secrets before sharing logs or screenshots.
